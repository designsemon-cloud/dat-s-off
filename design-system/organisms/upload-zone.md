# Organism → Upload Zone

> **Superseded.** `Landing.tsx` no longer renders either of these components — attaching screens (single or ordered multi) now happens inline inside [`organisms/prompt-composer.md`](prompt-composer.md)'s attachment-chip row. Kept on disk and documented as-is (not deleted — see `known-issues.md`) in case revived; build new work against `prompt-composer.md` instead. Note the "two different components, not one with a flag" reasoning below no longer holds in the composer, which _does_ handle both single and multi through one component — that became viable once both share the same compact chip-row visual, unlike the very different empty-state-hero vs. numbered-list-rows shapes these two originally had.

**Components**: [`UploadZone.tsx`](../../src/components/uxcc/UploadZone.tsx) (single file) and [`FlowUploadZone.tsx`](../../src/components/uxcc/FlowUploadZone.tsx) (ordered multi-file, built from [`molecules/upload-slot.md`](../molecules/upload-slot.md) rows). Two different components, not one component with a `multiple` flag — the empty-state/single-preview UX and the numbered-slot-list UX are different enough shapes that forcing one component to branch between them would have made both harder to read. Keep them separate if a third upload variant is ever needed, unless the two genuinely converge.

## Shared idioms between the two

- **Empty/dropzone state**: dashed border (`border-dashed border-border-strong`), `bg-bg-tertiary/50 backdrop-blur`, drag-over state swaps to `border-primary bg-primary/10 shadow-glow`. `FlowUploadZone`'s empty state is a flatter single-row variant of the same idiom (no large icon-in-circle), since it needs to stay compact once screens start filling in below it — the full-height centered dropzone treatment (`UploadZone`'s empty state, icon-feature-sized `Upload` icon in a `h-14 w-14` gradient circle) is reserved for the very first, most prominent upload moment on the page.
- **Accept types & size cap**: `image/png,image/jpeg,image/jpg,image/webp`, 5MB per file — identical validation in both. Any new upload surface should keep these exact constraints unless there's a specific product reason to change them (ask first).
- **Filled-state image treatment**: `object-contain` inside a `bg-bg-secondary` well for `UploadZone`'s single large preview (the whole image should be visible, nothing cropped, since it's the one thing the user is about to submit) vs. `object-cover object-top` for `FlowUploadZone`'s small row thumbnails (see `molecules/filmstrip-thumbnail.md` for why crop-from-top is correct for small thumbnails). **Don't swap these** — a single large preview should never crop, a small thumbnail should never letterbox.

## Flow-specific additions (new, not present in the single-screen version)

- Client-side compression (`src/lib/image-utils.ts`, `compressImageDataUrl`) runs on every file before it's stored — required because a multi-screen payload must stay under the ~4.5MB Vercel function body limit (see the Flow Analysis PRD for the full constraint). `UploadZone`'s single-file path does not compress today; if flow analysis has proven this works well, consider back-porting it to `UploadZone` too rather than letting the two diverge (ask before doing this — it's an existing-feature change, not a Flow Analysis change).
- A screen-count-aware helper line ("Add at least 2 screens to analyze a flow") appears only when relevant (`screens.length > 0 && screens.length < FLOW_MIN_SCREENS`) — this is the app's pattern for inline validation hints: quiet, `caption`-sized, `text-tertiary`, appears only once the user has started and is still under the minimum, never as a proactive/nagging hint before they've done anything.
